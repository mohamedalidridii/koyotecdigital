Scénarios de coûts cloud

Les prix changent selon la Région : nos clients sont à Paris, Francfort, aux Émirats et à Bahreïn.

01

Le trafic S3 qui passe par une NAT Gateway

Des charges de travail en sous-réseau privé lisent de gros volumes sur Amazon S3 : data lake, entraînement de modèles, traitement de logs. Par défaut, ce trafic sort par la NAT Gateway, qui facture chaque gigaoctet traité.

Configuration par défaut

Sous-réseau privé → NAT Gateway → S3. Chaque Go paie les frais de traitement de la NAT Gateway.

5 000 $US / mois

Architecture optimisée

Un VPC endpoint de type gateway pour S3 et une route dans les tables de routage privées : le trafic S3 va directement à S3 dans la Région. AWS ne facture rien de plus pour les gateway endpoints.

0 $US / mois

Vos chiffres

Prix utilisé: $0.05 / GB (NAT Gateway)

Économie estimée

5 000 $US / mois

60 000 $US / an

Vérifier mon compte AWS

Comment nous le mettons en place

  • Créer le gateway endpoint S3 (Terraform) et l'associer aux tables de routage privées.
  • Remplacer dans les bucket policies les conditions aws:SourceIp par aws:SourceVpce.
  • Vérifier dans Cost Explorer / CUR la baisse de NatGateway-Bytes.

Compromis à prévoir

  • Fonctionne pour S3 et DynamoDB, dans la même Région uniquement.
  • Les interface endpoints (PrivateLink) sont un autre produit, facturé à l'heure et au Go.
  • Les frais horaires de la NAT Gateway restent si d'autres flux en ont besoin.

02

Des microservices qui discutent entre zones de disponibilité

Dans un cluster Kubernetes (EKS) réparti sur plusieurs zones de disponibilité, les services s'appellent sans tenir compte de la zone. AWS facture le trafic entre instances de zones différentes 0,01 $ par Go dans chaque sens, soit 0,02 $ par Go pour un appel qui traverse.

Configuration par défaut

Pods répartis uniformément sur N zones : environ (N−1)/N des appels internes changent de zone.

6 667 $US / mois

Architecture optimisée

Des Services Kubernetes avec trafficDistribution: PreferSameZone (ou le load balancing par localité d'Istio) gardent les appels dans la zone de l'appelant dès qu'un endpoint sain y existe.

1 333 $US / mois

Vos chiffres

Prix utilisé: $0.01 / GB × 2 (out + in)

Économie estimée

5 333 $US / mois

64 000 $US / an

Vérifier mon compte AWS

Comment nous le mettons en place

  • Mesurer d'abord le trafic inter-zones (VPC Flow Logs ou la ligne DataTransfer-Regional-Bytes du CUR).
  • Activer PreferSameZone sur les Services les plus bavards et répartir les réplicas par zone (topology spread constraints).
  • Garder le repli : si une zone n'a pas d'endpoint sain, le trafic part ailleurs.

Compromis à prévoir

  • Chaque zone doit avoir assez de réplicas, sinon la charge devient inégale.
  • Tous les appels ne peuvent pas rester locaux : la part dépend de votre trafic.
  • AWS App Mesh n'est plus supporté depuis le 30 septembre 2026 : ne pas démarrer de nouvelle architecture dessus.

03

Des traitements batch avec état laissés en On-Demand

Des runners CI ou des traitements batch de plusieurs heures gardent un état sur disque : les équipes évitent alors les instances Spot, qui peuvent être interrompues avec un préavis de deux minutes, et paient le prix On-Demand en continu.

Configuration par défaut

Une flotte d'instances m5.2xlarge On-Demand (Linux), allumées tout le mois.

32 704 $US / mois

Architecture optimisée

La même flotte en Spot, avec l'état sur EBS ou des checkpoints sur S3. Au préavis d'interruption Spot de deux minutes, une règle EventBridge déclenche une automatisation qui sauvegarde le travail, déplace le volume vers une instance de remplacement et reprend.

13 033 $US / mois

Vos chiffres

Prix utilisé: m5.2xlarge: $0.448/h On-Demand · $0.1486/h Spot

Économie estimée

19 671 $US / mois

236 047 $US / an

Vérifier mon compte AWS

Comment nous le mettons en place

  • Prévoir des checkpoints (ou garder le répertoire de travail sur EBS).
  • Règle EventBridge sur EC2 Spot Instance Interruption Warning → Lambda / Step Functions pour vider, détacher et rattacher.
  • Plusieurs types d'instances (m5, m6i, m7i) et un repli On-Demand dans le groupe Auto Scaling.

Compromis à prévoir

  • Un volume EBS vit dans une seule zone : l'instance de remplacement doit être dans la même zone (ou utiliser des checkpoints S3 pour changer de zone).
  • Les prix Spot varient selon la zone et dans le temps, et la capacité n'est pas garantie.
  • Pour des tâches courtes sans état, plus simple : les relancer.

04

Une table DynamoDB avec une clé de partition « chaude »

Une table de classement ou d'ad-tech écrit des milliers d'éléments par seconde sous une seule clé par jour (par exemple 2026-11-18). Une partition DynamoDB accepte au maximum 1 000 unités d'écriture par seconde : au-delà, les écritures sont limitées (throttling) quelle que soit la capacité payée. Augmenter la capacité provisionnée coûte plus cher et ne règle pas la clé chaude.

Configuration par défaut

Une clé de partition par jour, et une capacité surdimensionnée pour tenter d'absorber le throttling.

22 542 $US / mois

Architecture optimisée

Le write sharding : un suffixe 0…N−1 ajouté à la clé répartit les écritures sur au moins pic ÷ 1 000 partitions, et l'on provisionne uniquement la capacité nécessaire (ou le mode à la demande).

11 271 $US / mois

Vos chiffres

Prix utilisé: $0.000772 / WCU-hour

Économie estimée

11 271 $US / mois

135 254 $US / an

Nombre minimum de shards: 20

Vérifier mon compte AWS

Comment nous le mettons en place

  • Choisir N avec de la marge (souvent 2× le minimum) et un suffixe aléatoire ou calculé (hash).
  • Lire en interrogeant les N shards en parallèle, ou maintenir un agrégat périodique.
  • Surveiller WriteThrottleEvents et les clés chaudes avec CloudWatch Contributor Insights.

Compromis à prévoir

  • Les lectures deviennent N requêtes (ou un agrégat à maintenir).
  • Une unité d'écriture couvre un élément jusqu'à 1 Ko : les éléments plus gros en consomment plus.
  • Sans sharding, plus de 1 000 écritures par seconde sur une même clé est impossible.

05

Des NAT Gateways dans chaque compte de dev et de staging

Les landing zones copient souvent le réseau de production dans chaque compte : une NAT Gateway par zone de disponibilité, « par parité ». Chacune est facturée à l'heure, au Go traité et pour son adresse IPv4 publique, même dans un compte de dev qui fait passer quelques centaines de gigaoctets par mois.

Configuration par défaut

Une NAT Gateway (avec son adresse IPv4 publique) dans chaque zone de chaque compte hors production.

1 455 $US / mois

Architecture optimisée

Une instance NAT t4g.nano par compte (8 Go gp3, une IPv4 publique), dans un groupe Auto Scaling d'une instance. Aucun frais de traitement au Go ; le trafic des autres zones paie le transfert inter-zones. Au-delà d'environ 1,2 To par mois, une instance par zone revient moins cher : le calculateur retient la moins chère des deux.

145 $US / mois

Vos chiffres

Prix utilisé: NAT Gateway $0.05/h + $0.05/GB · t4g.nano $0.0047/h · IPv4 $0.005/h · gp3 $0.0928/GB-mo

Économie estimée

1 310 $US / mois

15 715 $US / an

Configuration la moins chère ici : une instance NAT partagée par compte.

Guide complet, exemple chiffré et pièges →Vérifier mon compte AWS

Comment nous le mettons en place

  • Un module Terraform à deux variantes : NAT Gateways managées pour la production, instance NAT (image ARM fck-nat ou Amazon Linux 2023 avec masquerading) hors production.
  • Contrôle source/destination désactivé, interface réseau et Elastic IP fixes rattachées au démarrage, pour que les tables de routage privées restent valides après un remplacement.
  • Des gateway endpoints S3 et DynamoDB dans le même VPC, et une vérification dans Cost Explorer que NatGateway-Hours et NatGateway-Bytes tombent à zéro.

Compromis à prévoir

  • Une t4g.nano a 0,032 Gbit/s de bande passante réseau de base (5 Gbit/s en rafale) et 0,5 Gio de mémoire : suffisant pour du trafic de dev, pas pour de gros chargements de données.
  • Quand l'instance est remplacée, les connexions ouvertes tombent et la sortie s'interrompt quelques minutes. Gardez les NAT Gateways managées en production.
  • C'est un serveur à vous : à patcher, surveiller et alerter. Avec un ou deux comptes, l'économie justifie rarement ce travail.

Coûts cloud

À propos de ces chiffres

Ce sont les prix de ma facture ?

Ce sont les prix publics AWS de la Région choisie, vérifiés à la date indiquée. Votre facture peut être plus basse avec des Savings Plans, des instances réservées ou une remise négociée, et les prix Spot bougent chaque jour.

L'audit part de votre Cost and Usage Report : les chiffres sont les vôtres, pas des estimations.

Que livre l'audit des coûts cloud ?

Une revue de votre compte AWS en deux semaines : réseau (NAT, endpoints, trafic inter-zones), calcul (dimensionnement, Spot, Savings Plans), stockage et bases de données.

Vous recevez une liste priorisée d'économies, avec pour chacune l'effort, le risque et le montant mensuel attendu.

Travaillez-vous aussi sur Azure et Google Cloud ?

Oui. Les mêmes réglages par défaut existent (NAT, sortie de données, trafic entre zones, capacité inutilisée) ; les scénarios de cette page utilisent AWS car la plupart de nos clients y sont.

Pouvez-vous garantir les économies ?

Aucun ingénieur honnête ne peut garantir un montant avant d'avoir vu le compte. Nous nous engageons sur une mesure de départ, des changements relisibles dans le code (Terraform) et une comparaison avant/après sur votre facture.
